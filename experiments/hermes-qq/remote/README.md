# Luke Linux deployment

Run on the R2 host as a separate test stack, without modifying its gateway, account, services, or storage. Use rootless Podman and systemd user units from this directory. Node.js needs support for `node:sqlite`. The service files use this layout under `~/.local/share/luke-qq-pilot`:

- `code/`: checkout or deployment snapshot at the verified revision. After extracting under a private umask, set mode `0644` on the static files mounted into the containers: `shadow-config.yaml`, `worker-config.yaml`, `shadow.mjs`, `pilot.mjs` and `window-reply.mjs`. The parent directory remains private. Do not apply this mode to secrets or data.
- `inbox/`: existing QQ inbox and verified group binding, plus the SQLite receipts in `hermes-trial/`. Install the pinned QQ SDK from the test runtime's package manifest and lockfile in this directory.
- `deploy.env`: set `LUKE_NODE` to the absolute Node binary path, `LUKE_QQ_SDK` to the absolute SDK ESM entry path, and `LUKE_QQ_APP_ID` to the existing test-bot account, never the production R2 account.
- `secrets/`: private `qq-app-secret` (one line), `chat.env` and `work.env` (each containing the model credential and a separate API server key). The root and secrets directory must be private, and the files owner-only. Do not commit any of this state.

Before starting the receiver, stop any listener for the same test account. Migrate the inbox and receipts as closed SQLite files and check their integrity. Copy only portable state into the separate named volumes `luke-hermes-qq-chat-state` and `luke-hermes-qq-work-state`: transcripts, native databases (including any required WAL), memories and task state, not cache, process locks or machine-specific dependencies. Pull the pinned image in `run-profile.sh`; neither profile publishes a port or mounts the Podman socket. This host delegates the memory and pids controllers to user services, not the cpu controller; do not change host-wide delegation for this pilot.

Install the three `*.service` files in `~/.config/systemd/user/`, run `systemctl --user daemon-reload`, then enable both `luke-hermes-qq@{chat,work}.service`, `luke-qq-receive.service` and `luke-qq-bridge.service`. Verify both profile readiness probes, the QQ READY log and the bridge's cadence state separately. A ready socket does not prove a group reply was delivered. To pause, stop only these units and keep both volumes and the inbox.

Image-bearing work is staged in the private bridge receipts until all original bytes have been accepted as native Kanban attachments. Incomplete input staging expires after 24 hours; uploads that already reached Kanban follow native attachment retention. Update the work profile together with the bridge for this capability: Kanban workers need the `vision` toolset, while the work API stays restricted to `todo`.

## Honcho persistence probe

This is a remote, synthetic-only check, not a Luke deployment. Use upstream Honcho commit `894b88321872e01702a1aa638ddfdde6ad60f173` with its lockfile installed in `.venv` (no dev dependencies). Prefetch `cl100k_base` and `o200k_base` using that environment's `tiktoken` into the probe workspace's `token-cache/`. No production profile or credential file should be mounted or used.

Prepare a dedicated rootless `luke-honcho-probe` Podman pod with `--network none`, no published ports and an independent named volume. Put a PostgreSQL 15 service with pgvector in this pod as `luke-honcho-probe-pg`, listening only on loopback, with an empty `honcho_sandbox` database and the vector extension installed. Use the upstream pgvector image, or the official PostgreSQL 15 Bookworm image and the matching pgvector package verified against the signed PostgreSQL APT index. The database must not belong to another service.

Run `bash run-honcho-persistence-probe.sh <private-probe-workspace> <pinned-honcho-checkout>` on the remote host. It checks that the database belongs to the named pod and that the namespace exposes only loopback. It migrates the probe database, starts the upstream API and synthetic model under a clean environment, seeds two workspaces, restarts the API and database, and reads back the records from a new SDK process. Both phases must pass. Stop the pod after the test; retain the isolated volume only for reruns. Exact recall uses explicitly seeded conclusions, not a test of automatic inference or vector search quality.
